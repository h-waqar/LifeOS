# Plan 01-04.1: Close Authentication Boundary Race Conditions & Production Hardening

## 1. Plan Objective

Harden the LifeOS authentication boundary by closing the TOCTOU registration race condition with a PostgreSQL storage-engine enforced invariant (`single_user_lock` column with UNIQUE and CHECK constraints), proving the race condition is closed with concurrent integration tests against real PostgreSQL using a synchronization barrier, and performing a complete database invariant audit.

## 3. Architecture & Security Invariants

1. **Storage-Engine Enforced Single-User Invariant**:
   The `user` table enforces single-user cardinality at the storage layer via:
   - `single_user_lock boolean NOT NULL DEFAULT true`
   - `CONSTRAINT user_single_user_lock_unique UNIQUE (single_user_lock)`
   - `CONSTRAINT user_single_user_lock_check CHECK (single_user_lock = true)`
   No second row can be inserted by any client, ORM, SQL statement, or concurrent transaction.
2. **PostgreSQL Concurrency Guarantees**:
   Under concurrent inserts, PostgreSQL's unique B-tree index serializes insertion on the lock key `true`. The second transaction either blocks until the first commits and then fails with `23505 unique_violation`, or fails immediately.
3. **Fail-Closed and Consistent Rollback**:
   If a registration attempt fails due to constraint violation, all changes roll back cleanly under ACID guarantees, leaving exactly 1 user in PostgreSQL.
4. **Three-State Test Authenticity Contract**:
   - PostgreSQL offline + `REQUIRE_DB` unset -> Skip live test.
   - PostgreSQL offline + `REQUIRE_DB=true` -> Fail test suite immediately.
   - PostgreSQL online + `REQUIRE_DB=true` -> Execute against real database.
