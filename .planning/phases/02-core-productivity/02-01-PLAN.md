### 3.3 New Table: `task_dependencies`
Enforces composite cross-user isolation: a user can only declare dependencies between tasks that they own.
```typescript
export const taskDependencies = pgTable(
  "task_dependencies",
  {
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    userId: text("user_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    taskId: text("task_id").notNull(),
    dependsOnTaskId: text("depends_on_task_id").notNull(),
    createdAt: timestamp("created_at", { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [
    unique("task_dependencies_unique").on(
      table.userId,
      table.taskId,
      table.dependsOnTaskId
    ),
    foreignKey({
      name: "task_dependencies_task_fk",
      columns: [table.userId, table.taskId],
      foreignColumns: [tasks.userId, tasks.id],
    }).onDelete("cascade"),
    foreignKey({
      name: "task_dependencies_depends_on_task_fk",
      columns: [table.userId, table.dependsOnTaskId],
      foreignColumns: [tasks.userId, tasks.id],
    }).onDelete("cascade"),
    check(
      "task_dependencies_no_self",
      sql`${table.taskId} != ${table.dependsOnTaskId}`
    ),
    index("task_dependencies_user_task_idx").on(table.userId, table.taskId),
    index("task_dependencies_user_depends_idx").on(
      table.userId,
      table.dependsOnTaskId
    ),
  ]
);
```

### 3.4 Migration Strategy (`0007_task_management_extensions.sql`)
1. Run DDL to alter `tasks` table with new columns and check constraint for `energy_level`.
2. Create table `task_dependencies` with composite foreign keys.
3. Install PostgreSQL recursive trigger `trg_task_dependencies_prevent_cycle` to prevent dependency graph cycles:
   - Rejects immediate cycle (A depends on B when B already depends on A).
   - Rejects transitive cycle (A -> B -> C -> A) up to depth 50.
4. Grant standard permissions to role `lifeos_app` if role exists.

## 4. Priority Scoring Engine (Specification & Exact Formula)

> **Mandate:** Priority scoring must not use an undocumented or arbitrary formula. It must be deterministic, transparent, testable, and based directly on PRD Section 6 and DASH-02 requirements.

### 4.1 Input Fields & Allowed Ranges
1. `priority`: `"critical" | "high" | "medium" | "low"` (not null, defaults to `"medium"`)
2. `dueDate`: `Date | null`
3. `scheduledDate`: `Date | null`
4. `projectId`: `string | null` (active vs none)
5. `estimatedDuration`: `number | null` (minutes, 0..10080)
6. `status`: `"inbox" | "todo" | "in_progress" | "blocked" | "completed" | "cancelled"`
7. `hasUncompletedDependencies`: `boolean` (computed from `task_dependencies`)

### 4.2 Formula Components

$$\text{PriorityScore} = \text{BaseScore} + \text{DeadlineWeight} + \text{ScheduledWeight} + \text{ProjectWeight} + \text{EffortWeight} + \text{DependencyPenalty}$$

#### 1. Base Priority Score (Eisenhower Urgency/Importance)
- `critical` (P0): **100 points**
- `high` (P1): **70 points**
- `medium` (P2): **40 points**
- `low` (P3): **10 points**

#### 2. Deadline Weighting (`dueDate` relative to `referenceDate = now()`)
- `dueDate === null`: **0 points**
- `dueDate < now` (**Overdue**): **+50 points** base overdue boost + $\min(30, \lfloor\text{daysOverdue}\rfloor \times 5)$ points.
  *(Maximum overdue score is capped at +80 points to prevent unbounded runaway scores)*
- `dueDate` is **Today** (within $\le 24\text{ hours}$): **+40 points**
- `dueDate` is **Tomorrow** ($24\text{h} < t \le 48\text{h}$): **+25 points**
- `dueDate` is **This Week** ($2\text{d} < t \le 7\text{d}$): **+15 points**
- `dueDate` is **Next Week** ($7\text{d} < t \le 14\text{d}$): **+5 points**
- `dueDate` is **Future** ($> 14\text{ days}$): **0 points**

#### 3. Scheduled Date Proximity (`scheduledDate`)
- `scheduledDate <= today`: **+15 points** (indicates committed intention to work today)
- `scheduledDate > today` or `null`: **0 points**

#### 4. Project Alignment (`projectId`)
- `projectId !== null`: **+10 points** (part of an outcome-driven project)
- `projectId === null`: **0 points**

#### 5. Effort Weight (Quick-Win Momentum Factor)
- $\le 15\text{ minutes}$: **+5 points** (quick win that unblocks momentum)
- $16\text{ to }60\text{ minutes}$: **0 points**
- $> 60\text{ minutes}$: **-5 points** (demands dedicated deep focus block)
- `null`: **0 points**

#### 6. Blocked / Dependency Penalty
- `status === 'blocked'` OR `hasUncompletedDependencies === true`: **-50 points** (prevents blocked tasks from crowding actionable work)

#### 7. Terminal State Filter
- `status === 'completed'` OR `status === 'cancelled'`: **Score = 0**

### 4.3 Output Range & Normalization
- Raw score spans: `[0, 210]`.
- Output is an integer clamped between `0` and `250`.

### 4.4 Deterministic Tie-Breaking Rule
When two tasks have identical priority scores, rank ordering is strictly evaluated in this sequence:
1. `priorityScore` DESC
2. `dueDate` ASC (tasks due earlier take precedence; nulls sorted last)
3. `priority` severity DESC (`critical` > `high` > `medium` > `low`)
4. `createdAt` ASC (FIFO — older tasks prioritized to prevent starvation)
5. `id` ASC (lexicographical string comparison as absolute tie-breaker)

### 4.5 Storage vs Calculated Scoring Decision
- **Decision:** **Calculated dynamically at query/service time.**
- **Rationale:** Storing priority scores in database columns creates cache-invalidation hazards because scores decay and escalate as physical time passes. Calculating the score in pure TypeScript (`src/server/tasks/priority.ts`) using the query timestamp ensures 100% time accuracy, zero database write overhead, and identical scoring across client and server.

### 4.6 Documented Testable Edge Cases
1. *Zero inputs:* Task with low priority, no due date, no project, no estimate $\rightarrow \text{Score} = 10$.
2. *Maximum urgency:* Critical priority (100) + 10 days overdue (80) + active project (10) + quick win (5) $\rightarrow \text{Score} = 195$.
3. *Blocked critical:* Critical priority (100) + due today (40) - blocked penalty (50) $\rightarrow \text{Score} = 90$.
4. *Overdue capping:* Task 100 days overdue receives the same +80 cap as a task 6 days overdue.
5. *Midnight leap:* Reference time transitioning across 23:59:59 to 00:00:00 shifts deadline score from +25 (tomorrow) to +40 (today) cleanly.
6. *Completed task:* Score immediately evaluates to 0 regardless of priority or overdue status.

## 5. Recurrence Engine & Instance Generation

### 5.1 Recurrence Rule Schema (`RecurrenceRule`)
```typescript
export interface RecurrenceRule {
  frequency: "daily" | "weekly" | "monthly" | "custom";
  interval: number; // e.g. 1 = every day/week, 2 = every 2 weeks
  daysOfWeek?: number[]; // [1, 3, 5] for Mon, Wed, Fri
  endDate?: string; // ISO date string
  count?: number; // Maximum recurrences
}
```

### 5.2 Next Instance Calculation Algorithm (`calculateNextOccurrence`)
- Given `currentDueDate` (or `completedAt` if no due date) and `rule`:
  - `daily`: Add `rule.interval` days.
  - `weekly`: If `daysOfWeek` specified, find next matching day of week in sequence. Otherwise, add `rule.interval * 7` days.
  - `monthly`: Add `rule.interval` months, preserving day-of-month (clamping to month end if necessary, e.g. Jan 31 $\rightarrow$ Feb 28/29).
  - Check `endDate` and `count` limits; return `null` if series is exhausted.

### 5.3 Completion Hook & Transactional Spawn
When `updateTask` marks a recurring task as `completed`:
1. Execute inside PostgreSQL transaction (`tx`):
2. Current task is marked `completed`, `completedAt = now()`.
3. Compute `nextDueDate = calculateNextOccurrence(existing.dueDate, existing.recurrenceRule)`.
4. If `existing.scheduledDate`, compute `nextScheduledDate` shifting by the same interval.
5. Insert new task:
   - `title = existing.title`
   - `description = existing.description`
   - `status = "todo"`
   - `priority = existing.priority`
   - `energyLevel = existing.energyLevel`
   - `projectId = existing.projectId`
   - `estimatedDuration = existing.estimatedDuration`
   - `recurrenceRule = existing.recurrenceRule`
   - `dueDate = nextDueDate`
   - `scheduledDate = nextScheduledDate`
   - `parentTaskId = existing.parentTaskId`
   - `tags = existing.tags`
6. Create audit log: `task.recurrence_spawned` with `{ parentSeriesId: existing.id, newTaskId: inserted.id }`.

## 6. Task Dependency Management & Cycle Defense

### 6.1 Service Operations (`src/server/tasks/service.ts`)
1. `addTaskDependency(userId: string, taskId: string, dependsOnTaskId: string): Promise<TaskDependencyDTO>`
   - Validates ownership of both `taskId` and `dependsOnTaskId`.
   - Validates `taskId !== dependsOnTaskId`.
   - Executes recursive cycle check in PostgreSQL before insertion.
   - Creates atomic audit log `task.dependency_added`.
2. `removeTaskDependency(userId: string, taskId: string, dependsOnTaskId: string): Promise<{ success: true }>`
   - Deletes dependency row scoped strictly by `userId`.
   - Creates atomic audit log `task.dependency_removed`.
3. `getTaskDependencies(userId: string, taskId: string): Promise<{ blockedBy: TaskDTO[]; blocks: TaskDTO[] }>`
   - Returns tasks that `taskId` depends on (`blockedBy`) and tasks waiting on `taskId` (`blocks`).

### 6.2 PostgreSQL Dependency Cycle Prevention Trigger
```sql
CREATE OR REPLACE FUNCTION task_dependencies_prevent_cycle()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
  cycle_detected boolean := false;
BEGIN
  -- 1. Check self-dependency
  IF NEW.task_id = NEW.depends_on_task_id THEN
    RAISE EXCEPTION 'A task cannot depend on itself'
      USING ERRCODE = 'check_violation';
  END IF;

  -- 2. Check if depends_on_task_id already depends on task_id (directly or transitively)
  WITH RECURSIVE dependency_chain AS (
    SELECT depends_on_task_id, 1 as depth
    FROM task_dependencies
    WHERE task_id = NEW.depends_on_task_id AND user_id = NEW.user_id
    UNION ALL
    SELECT td.depends_on_task_id, dc.depth + 1
    FROM task_dependencies td
    JOIN dependency_chain dc ON td.task_id = dc.depends_on_task_id
    WHERE td.user_id = NEW.user_id AND dc.depth < 50
  )
  SELECT true INTO cycle_detected
  FROM dependency_chain
  WHERE depends_on_task_id = NEW.task_id
  LIMIT 1;

  IF cycle_detected THEN
    RAISE EXCEPTION 'Dependency cycle detected: adding this dependency would create a circular deadlock'
      USING ERRCODE = 'check_violation';
  END IF;

  RETURN NEW;
END;
$$;
```

## 7. Universal Quick Capture Architecture

### 7.1 Inline Syntax Parsing Engine (`src/server/tasks/quick-capture.ts`)
Zero-friction single-string parser extracting structured metadata:
- **Title:** All text not captured by tokens.
- **Priority:** `!p0` or `!critical` (critical), `!p1` or `!high` (high), `!p2` or `!medium` (medium), `!p3` or `!low` (low).
- **Due Date:** `^today`, `^tomorrow`, `^monday`..`^sunday`, `^YYYY-MM-DD`.
- **Scheduled Date:** `*today`, `*tomorrow`, `*YYYY-MM-DD`.
- **Energy Level:** `@high`, `@medium`, `@low` or `@energy:high` etc.
- **Project:** `#projectName` or `#projectId` (resolved against user's active projects via case-insensitive fuzzy prefix match).
- **Estimated Duration:** `~15m`, `~30m`, `~1h`, `~90m` (converted to integer minutes).
- **Tags:** `+tag1`, `+tag2`.

*Example:*
`"Finish Q3 tax report !high ^tomorrow #Finance @medium ~45m +taxes"`
Parses to:
```json
{
  "title": "Finish Q3 tax report",
  "priority": "high",
  "dueDate": "2026-09-15T23:59:59.999Z",
  "projectName": "Finance",
  "energyLevel": "medium",
  "estimatedDuration": 45,
  "tags": ["taxes"]
}
```

### 7.2 API Endpoint: `POST /api/tasks/quick-capture`
- Protected via `requireAuthenticatedUser(req)`.
- Input: `{ raw: string }` OR `{ raw: string, overrideProjectId?: string }`.
- Resolves project token against database inside transaction.
- Calls `createTask()` with full security, transaction bounds, and audit logging.
- Responds with HTTP 201 Created and `TaskDTO`.

### 7.3 UI Integration Points
1. **Global Keyboard Shortcut:** `C` or `Q` (when not inside an input) opens `QuickCaptureModal`.
2. **Command Palette (`Cmd+K`):** Top item is always "Quick Capture Task..." which activates the capture input directly.
3. **Dashboard / Tasks Views:** Prominent quick-capture bar at top of task lists.
