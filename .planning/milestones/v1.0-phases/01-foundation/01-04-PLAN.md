# Plan 01-04: Better Auth Authentication, Session Security & Server Authorization

## 1. Plan Objective

Implement the smallest production-grade authentication and authorization boundary required to move LifeOS from a hardened database foundation to a genuinely authenticated application. Wire Better Auth 1.7.4 into the existing Drizzle ORM singleton database client without creating secondary connection pools, enforce strict server-side session validation, implement fail-closed resource ownership authorization, establish single-user registration auto-lock (Decision D-01), provide CLI account recovery (`pnpm auth:reset`), and verify IDOR resistance through an adversarial test suite located strictly in `scripts/tests/phase-01/plan-04/`.

---

## 2. Exact Scope and Non-Goals

### In Scope
- **Better Auth Core Configuration**: `src/server/auth/index.ts` configuring Better Auth 1.7.4 with:
  - Drizzle adapter using the existing singleton `db` instance from `@/server/db` and foundational schema `authSchema`.
  - Passkey plugin configured via `getAuthConfig()` (`rpID`, `origin`).
  - Email and password authentication.
  - 30-day sliding session lifecycle (`expiresIn: 30 * 24 * 60 * 60`, `updateAge: 24 * 60 * 60`).
  - Secure cookie attributes (`HttpOnly`, `SameSite: "lax"`, `Secure` in production, `Path: "/"`).
  - Single-user registration auto-lock (Decision D-01): `hooks.before` and `databaseHooks.user.create.before` reject subsequent signups with 403 Forbidden once the primary owner exists.
  - Server-only runtime execution guard.
- **Server Authorization Boundary**: `src/server/auth/guard.ts` exporting:
  - `requireAuthenticatedUser(requestOrHeaders?)`: Resolves and validates session server-side; fails closed with 401 Unauthorized if invalid or missing.
  - `requireResourceOwnership(resourceUserId, authenticatedUserId)`: Enforces that access/mutation matches the session identity; fails closed with 403 Forbidden.
  - `withUserScope(condition, authenticatedUserId)`: Enforces query-level data filtering on authenticated user ID.
- **Audit Logging Service**: `src/server/audit/index.ts` exporting `createAuditLog()` to record authentication (login, logout, signup), security (password reset, session revocation), and mutation events into PostgreSQL `audit_log`.
- **User Preferences Domain Service**: `src/server/preferences/service.ts` proving ownership enforcement on the existing `user_preferences` table via query-level ownership checks (`WHERE user_id = authenticated_user_id`).
- **Route Handlers**:
  - `src/app/api/auth/[...all]/route.ts`: Better Auth route handler via `toNextJsHandler(auth.handler)`.
  - `src/app/api/preferences/route.ts`: User-scoped preferences API endpoint enforcing authentication and authorization.
- **CLI Account Recovery**: `scripts/auth-reset.ts` enabling owner password reset and session invalidation via CLI (`pnpm auth:reset`).
- **Client Auth Helper**: `src/lib/auth-client.ts` exporting a client-safe Better Auth client without leaking database or server secrets.
- **Adversarial Test Suite**: Located strictly in `scripts/tests/phase-01/plan-04/` covering:
  - Authentication lifecycle (signup, login, invalid credentials).
  - Single-user lock enforcement (403 on second registration).
  - Session lifecycle (validation, expiration, revocation, forged token rejection).
  - IDOR / Cross-user protection (cross-user read/write denial, parameter tampering).
  - Boundary isolation (server-only secrets never in browser bundles, no duplicate pools).
  - Live PostgreSQL integration testing adhering to the three-state authenticity contract (`REQUIRE_DB=true`).

### Non-Goals (Explicitly Out of Scope)
- Role-Based Access Control (RBAC) or Attribute-Based Access Control (ABAC) (LifeOS is a single-user system).
- Multi-tenancy, teams, or organization management.
- Third-party OAuth providers (Google/GitHub login deferred to Phase 8).
- Domain entity schemas (Tasks, Projects, Goals, Habits, Notes prohibited per vertical-slice rule).
- Application Shell UI (Sidebar, Command Palette Cmd+K deferred to Plan 01-05).

## 3. Architecture & Security Invariants

1. **Server-Side Identity Verification**:
   No client-supplied `userId` (in body, query, param, header, or unverified cookie) is ever trusted. Identity is derived strictly from `auth.api.getSession({ headers })`.
2. **Query-Level Ownership Enforcement**:
   Data queries and mutations enforce ownership in the SQL WHERE clause:
   ```sql
   WHERE id = $id AND user_id = $session_user_id
   ```
   Never fetch-then-check if query-level filtering is possible.
3. **Database Client Re-use**:
   Better Auth connects via `drizzleAdapter(db, { provider: "pg", schema: authSchema })` where `db` is the existing singleton from `src/server/db/index.ts`. No new `Pool` instances or ad-hoc connections are created.
4. **Fail-Closed Authorization**:
   Any missing, expired, malformed, or unverified session causes immediate termination with 401 Unauthorized before any business logic executes.
5. **Session Revocation Invalidation**:
   `auth.api.signOut` or session revocation immediately removes the session token from PostgreSQL `session` table, rendering subsequent requests using that token unauthenticated.
6. **Immutable Audit Logging**:
   Authentication lifecycle events are recorded in `audit_log`. The existing PostgreSQL triggers ensure audit log entries cannot be modified or deleted.

---

## 4. Test Authenticity Contract

All integration tests adhere to the project authenticity rule:
- `REQUIRE_DB=true`: PostgreSQL connection failure immediately causes tests to FAIL.
- `REQUIRE_DB` unset: PostgreSQL connection failure gracefully SKIPS live tests with a console notice.
- Real PostgreSQL available: All live authentication, session persistence, revocation, and IDOR tests execute against PostgreSQL.
- No tests mock database responses or swallow connection errors.
