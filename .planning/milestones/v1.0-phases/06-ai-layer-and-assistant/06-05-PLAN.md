**Phase:** Phase 6: AI Layer & Assistant  
**Plan:** 06-05  
**Status:** Planned

## 1. Objective

Deliver the security-critical Human-in-the-Loop (HITL) Confirmation Gate. Intercept all consequential and destructive tool calls from the AI model, persist them as previewable pending actions in `ai_actions` with a 5-minute time-to-live (TTL), prevent replay attacks, enforce database row locking during confirmation, execute approved mutations through domain services, and write comprehensive audit trails.

## 4. Detailed Implementation Specification

### 4.1 Confirmation Interception Protocol (`gate-service.ts`)
1. When the AI model invokes a tool with `riskTier !== 'tier1_readonly'` and `riskTier !== 'tier2_low'`:
   - Execution is halted before touching domain services.
   - Action preview is generated (`previewAction` function in tool definition).
   - An `ai_actions` record is created:
     - `status: 'pending'`
     - `expires_at: now() + 5 minutes`
     - `parameters: exact_arguments`
     - `preview_data: { summary, affectedEntities, diff }`
   - The tool execution returns a structured response to the model indicating the action is pending user approval.

### 4.2 Confirmation Execution Engine (`action-executor.ts`)
When the user clicks "Approve":
1. Open database transaction (`db.transaction`).
2. Lock row: `SELECT * FROM ai_actions WHERE id = ? AND user_id = ? FOR UPDATE`.
3. Validations (Fails Closed):
   - Status must be strictly `'pending'`. If already `'executed'` or `'rejected'`, fail with `409 Conflict`.
   - `expires_at > now()`. If expired, update status to `'expired'` and fail with `410 Gone`.
4. Dispatch to canonical domain tool executor with original parameters and authenticated `userId`.
5. Write immutable audit log record via `createAuditLog`:
   - `category: "mutation"`
   - `action: "ai.action_confirmed"`
   - `actor: "user:${userId}"`
   - `details: { toolName, parameters, actionId }`
6. Update `ai_actions` status to `'executed'`, record `executed_at` and `audit_log_id`.
7. Return execution result to client for conversation display.

## 5. Testing Strategy

All tests strictly placed in `scripts/tests/phase-06/plan-05/`.

### Unit Tests (`scripts/tests/phase-06/plan-05/hitl-gate.test.ts`):
- Intercepts Tier 3 and Tier 4 tools and creates pending action with 5-minute expiration.
- Auto-executes Tier 1 read-only tools without creating pending actions.
- Rejection transitions action status to `rejected` and records rejection reason.
- Expired actions are blocked from execution.

### Integration & Security Tests (`scripts/tests/phase-06/plan-05/hitl-security.integration.test.ts`):
- **Concurrency & Replay Defense:** Concurrent approval requests for the same action ID result in exactly one execution; the second request receives 409 Conflict.
- **Audit Verification:** Confirmed action creates a corresponding `audit_log` row with matching `actor` and `details`.
- **Multi-Tenant Protection:** User A cannot approve, reject, or inspect User B's pending action (fails with 403 Forbidden).
- **Tampering Defense:** Client cannot alter parameters during confirmation; the server executes strictly from the persisted database payload.

---

## 6. Acceptance Criteria

1. Consequential and destructive mutations cannot execute without explicit user approval.
2. Expired pending actions (>5 mins) fail closed and cannot be replayed.
3. Database locking guarantees single-use execution with zero race conditions.
4. Every confirmed execution writes an immutable audit log entry.
5. All tests in `scripts/tests/phase-06/plan-05/` pass with zero regressions.
