# Plan 05-02: Visual Content Calendar and Manual Performance Metrics Tracking

## 1. Plan Overview & Executive Context

- **Phase:** 5 — Content & Social Media
- **Plan Identification:** 05-02
- **Domain:** Editorial Scheduling, Visual Content Calendar, Publication Records, and Performance Analytics Engine
- **Prerequisites:** Phase 5 Plan 05-01 (Content idea capture, multi-platform drafts, and workflow status engine) implemented and verified. Phase 2 Calendar & Time Blocking architecture (`src/components/calendar/`) and Phase 4 Analytics calculation patterns (`src/server/finance/calculations.ts`) operational.
- **Goal:** Deliver the scheduling and performance feedback loop of LifeOS Content & Social Media: provide a visual editorial Content Calendar (Month, Week, and Timeline views) showing scheduled and published content pieces across all distribution channels; enable intuitive scheduling, date picking, rescheduling, and unscheduled ideas drawer; record publication details (live post URL, external post ID, publication timestamp); log manual performance metrics (impressions/views, likes, comments, shares, saves, link clicks); and calculate verified engagement metrics (total reach, channel engagement rate percentages, velocity, top-performing content ranking).
- **Requirements Satisfied:**
  - `CONT-03`: User can schedule content on a visual Content Calendar.
  - `CONT-05`: User can manually log or ingest performance metrics (impressions, likes, shares) for published content pieces.
- **Key Architectural Constraints:**
  1. **Vertical-Slice Rule**: Schema additions in Plan 05-02 are strictly restricted to `content_publications` and `content_metrics`. No premature AI schemas (Phase 6) or automated third-party OAuth sync schemas (Phase 8).
  2. **100% Deterministic Engagement Math**: All engagement metrics formulas (Total Engagements, Engagement Rate Percentage, Channel Averages) are isolated in a pure TypeScript calculation module (`src/server/content/calculations.ts`) with unit tests covering zero-impressions edge cases, rounding precision, and large values.
  3. **Decoupled from Live Social APIs**: External auto-publishing (`PUB-01`) is deferred to Phase 8. Plan 05-02 delivers complete manual publication records (`postUrl`, `externalPostId`) and manual metric logging. The schema is forward-compatible with automated Phase 8 background sync without breaking changes.
  4. **Timezone Determinism**: All schedule timestamps are stored as `timestamp with time zone` (`TIMESTAMPTZ`) in UTC. The user's preferred timezone (from Phase 1 preferences or browser) is used to project date boundaries into month/week calendar grids.
  5. **Composite Multi-Tenant Isolation**: `content_publications` and `content_metrics` enforce composite unique constraints `(userId, id)` and composite foreign keys `(userId, contentItemId)` / `(userId, publicationId)`. Cross-user publication or metric attachment is prohibited at the database level.
  6. **Clean Repository & Test Organization**: All tests reside strictly in `scripts/tests/phase-05/plan-02/`. Zero test files inside `src/`.

      .primaryKey()

    postUrl: text("post_url"),
    externalPostId: text("external_post_id"),
    notes: text("notes"),

    index("content_publications_user_item_idx").on(

export interface MetricInputs {
  views: number;
  likes: number;
  comments: number;
  shares: number;
  saves: number;
  clicks: number;
}

/**
 * Calculates total engagements from granular interaction counts.
 */
export function calculateTotalEngagements(inputs: MetricInputs): number {
  return (
    Math.max(0, inputs.likes) +
    Math.max(0, inputs.comments) +
    Math.max(0, inputs.shares) +
    Math.max(0, inputs.saves) +
    Math.max(0, inputs.clicks)
  );
}

/**
 * Calculates engagement rate as a percentage rounded to 2 decimal places.
 * Returns 0.00 when views is 0 to prevent division by zero.
 * Formula: ((likes + comments + shares + saves + clicks) / views) * 100
 */
export function calculateEngagementRate(inputs: MetricInputs): number {
  const views = Math.max(0, inputs.views);
  if (views === 0) return 0;

  const totalEngagements = calculateTotalEngagements(inputs);
  const rate = (totalEngagements / views) * 100;
  return Math.round(rate * 100) / 100;
}

## 5. Service Layer Architecture & API Design

### 5.1 Content Calendar Service: `src/server/content/calendar-service.ts`
- `getCalendarItems(userId, { startDate, endDate, platform })`: Queries publications and scheduled content items within the date window. Returns day-by-day mapping with entity titles, platform variant types, and status.
- `schedulePublication(userId, input)`: Schedules a content item or variant for a specific date and platform. Transitions content item status to `scheduled`.
- `reschedulePublication(userId, publicationId, newScheduledFor)`: Updates target publication datetime.
- `markAsPublished(userId, publicationId, { publishedAt, postUrl, externalPostId })`: Sets publication status to `published`, records live URL, and updates content item status to `published`.

### 5.2 Content Metrics Service: `src/server/content/metrics-service.ts`
- `logMetrics(userId, contentItemId, publicationId, input)`: Validates inputs, computes engagement rate, inserts snapshot into `content_metrics`, and records audit event.
- `getMetricsHistory(userId, publicationId)`: Returns time-series of metrics recorded for a publication.
- `getAggregateAnalytics(userId, { startDate, endDate })`: Computes top-level stats: Total Reach, Total Engagements, Overall Avg Engagement Rate, Posts Published in period, Platform comparison breakdown, and Top 5 performing posts ranked by engagement rate.

### 5.3 Zod Schemas: `src/server/content/validation.ts` (Additions)
- `scheduleContentSchema`:
  - `contentItemId`: UUID string
  - `variantId`: optional UUID string
  - `platform`: enum (`twitter`, `linkedin`, `blog`, `instagram`, `youtube`, `newsletter`, `other`)
  - `scheduledFor`: ISO timestamp string
- `markPublishedSchema`:

### 5.4 API Endpoints
- `GET /api/content/calendar`: Retrieve scheduled and published items for a date range.

## 7. Security Model & Multi-Tenant Authorization

1. **Strict User Ownership**: `content_publications` and `content_metrics` require verified `user_id`. Queries join and filter strictly on `where(eq(table.userId, user.id))`.
2. **Composite Foreign Key Invariants**:
   - `content_publications` composite FK `(userId, contentItemId)` references `content_items(userId, id)`.
   - `content_metrics` composite FK `(userId, publicationId)` references `content_publications(userId, id)`.
   Prevents any metric from being attached to a publication owned by another user.
3. **Audit Trail**: Recording publication live URLs or publishing status changes writes to `audit_log` with `category = 'mutation'`, `action = 'content.published'`.
